# Reverse Engineer a Project to Its Architecture

I want to create a file `ARCHITECTURE.md` in any project.

The developer (me) will provide a file `ARCH-SPECS.md` where he will put the requirements used by the AI to generate `ARCHITECTURE.md`.

The developer will engage a brainstorming session with the AI to discover what is needed in `ARCH-SPECS.md`.

The purpose of this exercise is to take a legacy project and add two files:

- `ARCH-SPECS.md` (initially an empty file)
- `ARCHITECTURE.md` (generated by the AI)

These files will provide the context and requirements needed so that UML diagrams (Mermaid Diagrams as Code) and a description of the architecture of the legacy project can be generated in `ARCHITECTURE.md`.

`ARCH-SPECS.md` will specify what goes into `ARCHITECTURE.md`.

The brainstorming takes place first. When that is complete, the AI generates `ARCHITECTURE.md`.

We need to assume that the developers did not specify technologies, modules, dependencies, business rules, design decisions, or constraints.

So we need to discover them and describe them in `ARCHITECTURE.md`.

This also includes networking, databases, and other requirements.

The purpose of the brainstorming is for the AI to get the developer to answer questions needed to do this exercise.
The AI must inspect the actual source code and configuration files before documenting architectural findings.
The AI must not halucinate if it does not understand any thing it must prompt the developer for input 
The AI must not invent architectural decisions simply because they are common practices.
The AI may read all project files but may write only to ARCH-SPECS.md and ARCHITECTURE.md


## The purpose of the exercise is to identify:

- Project purpose and business domain
- System boundaries and external systems
- Application architecture and architectural patterns
- Modules, components and their responsibilities
- Technologies, frameworks and versions
- Dependencies and dependency relationships
- Database architecture, schemas and data relationships
- Networking, protocols, ports and communication flows
- APIs, endpoints and integrations
- Business rules and workflows
- Authentication, authorization and security
- Configuration, environment variables and secrets
- Deployment architecture and infrastructure
- Build, startup and execution processes
- Logging, error handling and monitoring
- Testing architecture
- Architectural constraints and technical debt
- Design decisions that can be inferred from the code
- Mermaid diagrams illustrating the architecture

## What else needs to be identified

- Project structure: directory structure, file organization and naming conventions
- Data flow: how data moves through the application
- Component interactions: which components communicate and how
- State management: where application state lives and how it changes
- Concurrency: threads, asynchronous processing, queues and background jobs
- Caching: cache mechanisms, locations and invalidation
- Data lifecycle: data creation, modification, retention, archival and deletion
- Transactions: transaction boundaries, consistency and rollback
- Scalability: bottlenecks, scaling mechanisms and limitations
- Resilience: retry mechanisms, timeouts, failover and recovery
- Performance: resource requirements and performance-sensitive components
- User interface: frontend architecture, navigation and interaction with the backend
- Operational requirements: backup, restore, maintenance and disaster recovery
- Technical debt: known problems, obsolete components and architectural weaknesses
- Evidence references: file paths and relevant code locations supporting architectural findings
- Assumptions and uncertainties
- Identified architectural risks
- Glossary of domain-specific terminology

## Classification of findings

The AI must distinguish between four types of findings:

- **Verified:** Directly established from source code or configuration.
- **Inferred:** Strongly suggested by the implementation.
- **Unknown:** Cannot be established from available evidence.
- **Contradictory:** Different parts of the project suggest conflicting information.



## ARCH-SPECS.md creation and population
- The AI must begin by conducting an interactive brainstorming session with the developer.
- The AI must ask questions, one at a time, to discover the developer's requirements for ARCHITECTURE.md.
- The AI must not assume answers or make architectural decisions on behalf of the developer.
- The AI must use the developer's answers to establish the contents and structure of ARCH-SPECS.md.
- The AI must suggest additional requirements where necessary.
- The developer must approve the proposed contents before the AI writes ARCH-SPECS.md.
- Once approved, the AI must create and populate ARCH-SPECS.md in the project's root directory.
- The AI must verify that ARCH-SPECS.md contains the agreed requirements.
- Only after ARCH-SPECS.md has been completed and approved may the AI begin generating ARCHITECTURE.md.
- The AI must use ARCH-SPECS.md as the authoritative specification for generating ARCHITECTURE.md.

## Mermaid diagrams

Where applicable, `ARCHITECTURE.md` should include:

- System context diagram
- Deployment diagram
- Component dependency diagram
- Database entity relationship diagram
- Sequence diagrams for important business workflows
- Communication and networking diagram

Each diagram must be accompanied by a description explaining what it represents.
